Architecture · deep dives

How I structure large Android apps.

Three patterns I keep reaching for. Each one is a write-up from a real production codebase — not slideware.

Pattern · 01

Modular monolith · 47 modules

app → feature:* → core:*
  • Convention plugins for build consistency
  • Feature modules hidden behind :api modules
  • DI graph per feature, app-level aggregator
  • Build cache: 4m → 38s on M-series MBP
  • Strict module-rules Detekt rules
Pattern · 02

UDF + StateFlow · predictable UI

Intent → Reducer → State
  • One immutable UiState per screen
  • Side-effects as suspend functions, not state
  • Single StateFlow per ViewModel
  • Compose collectAsStateWithLifecycle everywhere
  • Turbine for unit tests, no mocking framework
Pattern · 03

Offline-first sync · CRDT

Device ⇄ CRDT log ⇄ Server
  • Append-only op-log, last-write-wins + tombstones
  • Lamport-clock ordering for causality
  • Conflict-free merge by construction
  • Works offline for > 30 days without sync
  • End-to-end encrypted with libsodium-jvm

Code philosophy

How I think about code.

Principle · 01

Boring code wins.

Cleverness is a tax on your colleagues. Prefer the obvious answer that someone can debug at 3am.

Principle · 02

Make the change easy, then make the easy change.

Kent Beck. Most "hard" problems are caused by an earlier short-cut.

Principle · 03

Optimise for the next reader.

You write code once. Someone else reads it a hundred times. Name accordingly.

Principle · 04

Delete code. Then delete more.

Every line you ship is a line someone has to maintain. The empty line is the only one that costs nothing.
